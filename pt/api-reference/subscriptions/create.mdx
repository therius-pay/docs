`POST /subscription` inscreve um cliente em um plano e estabelece o mandato recorrente que
ancora toda futura Merchant Initiated Transaction (MIT). Inscrever um cliente é uma
Cardholder Initiated Transaction (CIT), e uma CIT pode exigir 3D Secure. Dois modos:

<SchemaLangNote lang="pt" />

<CardGroup cols={2}>
  <Card title="Modo CIT — nonceData / cardData" icon="credit-card">
    O Therius executa a CIT inicial + a primeira cobrança aqui. O cliente deve estar presente. Essa CIT
    **não pode realizar um desafio de 3D Secure** — um cartão que exige 3DS falhará.
  </Card>
  <Card title="Modo record — tokenData" icon="shield-check">
    O token é um cartão que **já concluiu uma CIT** (incluindo 3DS) por meio de
    `/payment/authorization` ou `/payment/purchase`. Nenhuma segunda CIT é executada aqui.
    **Use isto para qualquer cartão que precise de 3D Secure.**
  </Card>
</CardGroup>

Forneça o cartão como **exatamente um** instrumento — `nonceData`, `cardData` (apenas servidores
em conformidade com PCI DSS), ou `tokenData`.

<Warning>
  `cardOnFile` e `instalments` são ignorados aqui — o Therius é dono do mandato. No modo record
  `networkTransactionId` / `networkReferenceId` são lidos do token; passe-os apenas para um
  cartão cuja CIT foi feita fora do Therius.
</Warning>

## Modo record

Execute você mesmo uma CIT com capacidade 3DS, depois anexe o resultado:

<Steps>
  <Step title="Execute a CIT via /payment/*">
    Chame `/payment/authorization` (valor 0 = verificação de conta) ou `/payment/purchase`
    com `card.<x>.tokenize: true` + um `shopper.id`, e trate qualquer desafio de 3DS com o
    SDK JS como você faria para um pagamento normal. A resposta devolve um token `vt_...`.
  </Step>
  <Step title="Crie a assinatura">
    `POST /subscription` com `card.tokenData.token`. Para o ciclo 1:
    <br />• teste ou `startAt` diferido → nada é cobrado;
    <br />• você cobrou o primeiro ciclo na sua CIT (`/payment/purchase`) → passe também
    `firstPaymentId` (o `id` do pagamento da resposta dessa chamada); o Therius marca a primeira
    fatura como paga e a vincula, sem cobrança;
    <br />• a sua CIT foi uma verificação de valor zero → omita `firstPaymentId`; o Therius cobra
    o ciclo 1 como uma MIT contra o mandato registrado (reverte a assinatura com um `402`
    se for recusada).
    <br />O objeto `firstCycle` da resposta informa o que aconteceu.
  </Step>
</Steps>

## Requisição

**URL base:** `https://api.therius.io/v1`

**Endpoint:** `POST /subscription`

### Headers

<ParamField header="Authorization" type="string" required>
  `Bearer sk_live_xxx` (produção) ou `Bearer sk_sandbox_xxx` (sandbox) — a sua chave de API privada de lojista.
</ParamField>

<ParamField header="Content-Type" type="string" required>
  `application/json`
</ParamField>

<ParamField header="Idempotency-Key" type="string">
  Um UUID que você gera por operação. Repetir com a mesma chave devolve a resposta original em vez de repetir a operação. Recomendado em produção.
</ParamField>

### Corpo da requisição

<ParamField body="merchantCode" type="string" required>
  O seu identificador único de conta de lojista.
</ParamField>

<ParamField body="planId" type="integer" required>
  O ID de um plano de faturamento ativo. O plano determina o valor, a moeda, o intervalo e a configuração de teste.
</ParamField>

<ParamField body="customerEmail" type="string">
  Endereço de e-mail do cliente. Usado para notificações de faturamento e comunicações de gestão de cobranças.
</ParamField>

<ParamField body="customerName" type="string">
  Nome completo do cliente como deve aparecer nas faturas.
</ParamField>

<ParamField body="customerDocument" type="string">
  ID nacional ou número de documento fiscal do cliente. Obrigatório em alguns países (p. ex. CPF/CNPJ do Brasil). Verifique a configuração `availableCountries` do plano para os requisitos locais.
</ParamField>

<ParamField body="card" type="object" required>
  Dados de cartão para a CIT inicial. Forneça **exatamente um** dos instrumentos abaixo — são alternativas intercambiáveis, não campos para combinar.

  <Expandable title="instrumentos de card — escolha um">
    <ParamField body="card.nonceData.nonce" type="string">
      Um nonce novo de uso único do SDK JS do Therius. Recomendado — nenhum dado de cartão toca o seu servidor. Os nonces são de uso único e expiram após uma janela curta.
    </ParamField>
    <ParamField body="card.cardData" type="object">
      Campos de cartão brutos — `cardNumber`, `expiryMonth`, `expiryYear`, `cvv`, `cardholderName` (e `documentNumber`, `cardAddress` opcionais). Apenas se o seu servidor estiver em conformidade com PCI DSS para tratar PANs brutos.
    </ParamField>
    <ParamField body="card.tokenData.token" type="string">
      **Modo record.** Um vault token `vt_...` para um cartão que já concluiu a sua CIT.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="firstPaymentId" type="string">
  Somente no modo record, e apenas quando há um primeiro pagamento devido (ignorado para assinaturas
  com teste ou diferidas). O `id` do pagamento devolvido pela chamada a `/payment/authorization` ou
  `/payment/purchase` na qual você executou a CIT para este cartão. O Therius valida que é um
  pagamento `captured` ou `authorized` na sua conta que cobrou o **mesmo vaulted token** e que está na
  **moeda do plano**, depois marca a fatura do ciclo 1 como paga e a vincula — sem cobrança.
  Quando omitido, o Therius cobra o ciclo 1 como uma MIT contra o mandato registrado.
</ParamField>

<ParamField body="metadata" type="object">
  Pares chave/valor arbitrários que você quer anexar à assinatura. Os valores devem ser strings. Devolvidos em todas as respostas de assinatura e cargas de webhook.
</ParamField>

<ParamField body="startAt" type="string">
  Timestamp RFC 3339 para uma data futura para adiar a primeira cobrança, p. ex. `"2025-09-01T00:00:00Z"`. Se omitido, a assinatura é ativada e cobrada de imediato (ou no fim de um teste se o plano tiver um).
</ParamField>

<ParamField body="parentSubscriptionId" type="string">
  UUID de uma assinatura existente para designar como a pai. Usado para modelar hierarquias de assinatura (p. ex. um plano base e complementos).
</ParamField>

<ParamField body="propagateLifecycle" type="boolean">
  Quando `true`, os eventos de pausar e cancelar na assinatura pai são propagados automaticamente em cascata para esta assinatura filha. Requer `parentSubscriptionId`.
</ParamField>

## Resposta

Uma requisição bem-sucedida devolve `201 Created` com o objeto de assinatura completo, incluindo o `id` da assinatura, o `status` inicial, as datas de início e fim do período atual, e a primeira fatura.

### Status na criação

| Status | Quando ocorre |
| --- | --- |
| `active` | O plano não tem teste; a primeira cobrança teve sucesso. |
| `trialing` | O plano tem um `trialPeriodDays` configurado. |
| `past_due` | A CIT inicial falhou. Raro — normalmente um `402` é devolvido na recusa em vez disso. |

## Erros

| Código | Significado |
| --- | --- |
| `400` | Plano não encontrado ou inativo; ou (modo record) o token não carrega nenhum mandato de CIT, ou `firstPaymentId` não se resolve a um pagamento liquidado que cobrou este token. |
| `402` | A cobrança da CIT inicial foi recusada (modo CIT), ou a MIT do primeiro ciclo foi recusada (modo record — a assinatura é revertida). |
| `409` | `Idempotency-Key` duplicado com um corpo de requisição em conflito. |
| `422` | Erro de validação — p. ex. nenhum instrumento de cartão fornecido, um nonce expirado/usado, ou um plano inválido. |
